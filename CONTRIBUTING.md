# Как участвовать

Спасибо, что хотите помочь Docpoint. Ниже правила, по которым проект принимает
изменения. Они короткие, но без них ревью затягивается.

## С чего начать

- **Нашли баг.** Откройте issue: шаги воспроизведения, что ожидали и что
  получили, ОС и версия приложения. Если приложение падает или молчит,
  приложите хвост `logs/docpoint.log` из каталога данных, путь описан в README.
- **Небольшая правка.** Опечатка, очевидный баг, уточнение в документации:
  присылайте pull request сразу.
- **Новая функция или изменение поведения.** Сначала issue с описанием, что и
  зачем. Обсудим подход до того, как вы потратите на него вечер.

Настройка окружения, первый запуск и сборка описаны в README, раздел
«Локальная разработка».

## Ветки

- Pull request открывается в `main`.
- Ветка создаётся от актуального `main` и называется по схеме
  `<тип>/<что-меняется>`: только строчные латинские буквы, цифры и дефис, два
  пять слов о сути изменения. Номер issue, если есть, идёт сразу после типа.

  | Тип | Когда |
  | --- | --- |
  | `feat` | новая возможность |
  | `fix` | исправление |
  | `refactor` | перестройка без изменения поведения |
  | `docs` | README, docs, комментарии |
  | `chore` | зависимости, конфигурация, обслуживание |
  | `ci` | workflows и проверки |
  | `test` | только тесты |

  Примеры: `feat/erd-import-mysql`, `fix/42-markdown-scroll-lag`,
  `docs/contributing`, `chore/tauri-2.3`.

- Одна ветка решает одну задачу. Два несвязанных изменения это два PR.

## Коммиты

- Тема коммита это одно предложение по-русски о результате, как строка в
  списке изменений: «Читалка markdown не тормозит на прокрутке». Темы вроде
  «patch», «fix», «wip», «правки» не принимаются.
- Тело коммита по желанию. Если пишете, объясняйте, почему сделано так, а не
  что сделано: что изменилось, видно в диффе.
- PR сливается через squash, поэтому промежуточные коммиты внутри ветки
  вылизывать не нужно. Темой итогового коммита станет заголовок PR.

## Код

- **Фронтенд** следует Feature-Sliced Design: слой импортирует только
  нижележащие слои, наружу слайс отдаёт только `index.ts`. Слои, сегменты и
  соглашения об именовании описаны в `CLAUDE.md`, соблюдение проверяет
  `bun run lint:arch`. SVG-иконки живут только в `src/shared/svg`.
- **Бэкенд** разделён на `domain`, `repository`, `service` и
  `infrastructure`, зависимости идут в ту же сторону. Изменение схемы базы это
  новый файл в `src-tauri/migrations` со следующим номером. Уже существующие
  миграции не редактируются: они применены у пользователей.
- **Язык.** Идентификаторы в коде на английском. README, документация,
  комментарии и тексты интерфейса на русском.
- **Зависимости.** Новую зависимость обоснуйте в описании PR. Её лицензия
  должна быть совместима с AGPL-3.0: MIT, Apache-2.0, BSD, ISC, MPL-2.0
  подходят.

## Проверки перед PR

Те же команды выполняет CI на каждый push и pull request. Слияние возможно
только с зелёным CI.

```bash
bun run lint                     # Biome с автоисправлением; в CI: bunx biome ci src
bun run wasm && bun run build    # типы и сборка фронтенда

cd src-tauri
cargo fmt
cargo clippy --all-targets -- -D warnings
cargo test
```

## Pull request

- Заполните шаблон: что изменилось, зачем, как проверить. Для изменений в
  интерфейсе приложите скриншот или короткую запись.
- Небольшой PR ревьюится быстрее. Большое изменение лучше разбить на
  несколько последовательных.
- На замечания ревью отвечайте новыми коммитами, а не force-push: так видно,
  что именно поменялось после обсуждения.

## Лицензия

Docpoint распространяется под AGPL-3.0-or-later. Отправляя pull request, вы
соглашаетесь, что ваш код распространяется на тех же условиях.
