# Формат ответа REST API

Область действия: контракт тела, который бэкенд отдаёт на **любой**
JSON-эндпоинт. Знание этого контракта не
привязано к конкретной сущности — он общий для всех `{entity}ApiResponse` из
[api.md](./api.md), поэтому вынесен отдельно.

У сервиса ровно два тела ответа: успех и ошибка. Третьего нет — ни голого
массива в корне, ни `text/plain` от сервера при 404/405, ни пустого тела.
Парсинг на фронте должен полагаться на это без запасных веток.

---

## 1. Успех

```json
{
  "data": {
    "symbol": "BTCUSDT",
    "price": "64000.5",
    "ts": 1756725822000
  },
  "meta": {
    "request_id": "21dae3484af6dd1e8c47bc32",
    "timestamp": "2026-09-01T10:43:42Z"
  }
}
```

```typescript
// src/shared/api/types/envelope.ts
export interface ApiSuccessResponse<T> {
  data: T;
  meta: ApiMeta;
}
```

- `data` присутствует **всегда** — объект или массив. Пустая коллекция
  приходит как `[]`, никогда как `null` и никогда не отсутствует. Значит,
  `response.data.data ?? []` на фронте — защита от лишнего случая, которого
  контракт не допускает; писать его не нужно.
- Успешный HTTP-статус — **200** по умолчанию. `201`/`202`/`204` только там,
  где у ответа реально другая семантика.
- Денежные величины (`price`, `qty` и т.п.) приходят **строками**, не
  числами — `float` в JS теряет точность точно так же, как в Go. Парсить
  через `parseFloat` только там, где точность не критична (для расчётов —
  через decimal-библиотеку, не встроенный `number`).
- Ключа `error` в успешном ответе не бывает.

## 2. Ошибка

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "rate limited",
    "details": {
      "exchange": "binance_futures",
      "exchange_code": "-1003",
      "exchange_message": "Too many requests"
    }
  },
  "meta": {
    "request_id": "21dae3484af6dd1e8c47bc32",
    "timestamp": "2026-09-01T10:43:42Z"
  }
}
```

```typescript
// src/shared/api/types/envelope.ts
export interface ApiErrorResponse {
  error: {
    code: string;               // стабильный SCREAMING_SNAKE-enum
    message: string;            // текст для человека, не парсить
    details?: Record<string, unknown>;
    violations?: ApiViolation[];
  };
  meta: ApiMeta;
}
```

- **`code`** — единственное поле, по которому фронту разрешено ветвиться
  (`if (error.code === "RATE_LIMITED")`). Текст `message` — только для
  показа/лога, набор его значений не стабилен.
- **`details`** — открытый объект атрибутов ошибки (например, код и текст
  биржи при `EXCHANGE_ERROR`). Неизвестные ключи фронт игнорирует, а не
  падает на них.
- **`violations`** — опционально, и его отсутствие тоже информативно: значит
  «дело не в форме запроса». Пустым массивом не отдаётся, поэтому
  `error.violations?.length` — корректная проверка «есть ли ошибки формы».

### 2.1. Нарушения формы запроса (`violations`)

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "validation error",
    "violations": [
      { "field": "qty",   "message": "qty must be positive" },
      { "field": "price", "message": "price is not a valid decimal" }
    ]
  },
  "meta": { "request_id": "21dae3484af6dd1e8c47bc32", "timestamp": "2026-09-01T10:43:42Z" }
}
```

```typescript
export interface ApiViolation {
  field: string;     // путь через точку: "qty", "legs.0.price", "" — запрос целиком
  message: string;
}
```

- `field` — путь до поля запроса через точку (без ведущей `.`), **в тех
  именах, в которых фронт его отправил** (`snake_case`, как в DTO), а не во
  внутренних доменных именах. Поэтому подсветка поля формы на фронте — это
  прямое сопоставление `field` → имя поля DTO/формы, без дополнительного
  маппинга. Пустая строка — межполевая ошибка, привязывать её к конкретному
  инпуту нельзя, показывать как ошибку формы целиком.
- Порядок элементов значим — это порядок полей формы, рисовать сообщения
  нужно в этом порядке, а не сортировать по алфавиту/важности.
- Один `field` — одно нарушение: если бэкенд не смог разобрать значение,
  второй проверки (например, диапазона) для того же поля не будет.

## 3. `meta` — общая часть успеха и ошибки

```typescript
export interface ApiMeta {
  request_id?: string;   // тот же request_id, что и в заголовке X-Request-Id
  timestamp: string;     // RFC 3339, UTC
}
```

`meta` одинакова у успеха и у ошибки намеренно: `request_id` для тикета в
саппорт достаётся одним и тем же путём независимо от исхода запроса —
`response.data.meta.request_id` (или `error.response.data.meta.request_id`
в catch-ветке axios), без ветвления «если ошибка — бери из заголовка».

## 4. Как это ложится на паттерн API-функции

Дополняет [api.md, §2.1–2.2](./api.md): `{Entity}ApiResponse` из `types/type.ts`
— это тип **значения `data`**, а не всего тела ответа. Тело обёрнуто в
конверт снаружи:

```typescript
// src/entities/{entity}/api/get-{entity}-api.ts
import type { ApiSuccessResponse } from "@/shared/api/types/envelope";
import type { {Entity}ApiResponse } from "./types/type";

export async function get{Entity}Api(params: Get{Entity}Params): Promise<{Entity}> {
  const response = await axiosClientCentralManager.get<ApiSuccessResponse<{Entity}ApiResponse>>(
    `/{entities}/${params.id}`,
  );
  return map{Entity}(response.data.data);
}
```

Ошибку разбирает **общий** axios-интерцептор (не каждая API-функция по
отдельности): он читает `error.response.data` как `ApiErrorResponse` и
приводит к доменной ошибке фронта (код + сообщение + `violations`, если
есть). API-функции выше по стеку ловят уже эту доменную ошибку, а не сырой
axios-`AxiosError`.

## 5. Статусы, значимые для фронта

| Статус | Что означает | Реакция фронта |
|---|---|---|
| `200` | успех | — |
| `400` | форма запроса не прошла валидацию | единственный класс, где стоит ждать `violations` — подсветить поля формы |
| `401` | нет валидной аутентификации | разлогинить / обновить токен и повторить один раз |
| `403` | аутентификация есть, доступа нет | показать отказ, повтор бессмысленен |
| `404` / `405` | ресурса/маршрута нет | не ретраить, это баг клиента или мёртвая ссылка |
| `429` | лимит запросов | ждать `Retry-After` (секунды), затем повторить — если `retryable: true` |
| `5xx` | сбой на стороне бэкенда/апстрима |

`Retry-After` (секунды) обязателен при `429` и на любом ретраибельном
ответе — значение апстрима, если он его прислал, иначе дефолт сервиса.
Клиентский ретрай-хелпер должен читать этот заголовок, а не хардкодить
интервал.
