# Дерево каталогов

Единая группировка документов Docpoint: каталоги, doc-api, doc-ws, ERD,
markdown и загруженные файлы — узлы одного дерева внутри платформы.

До этого группировок было две: домены (строки в БД, к которым «прикреплялись»
документы) и отдельное файловое дерево markdown-файлов на диске (vault, со
своими путями и областями видимости). Ни одна не показывала всё содержимое
платформы разом. Обе заменены деревом узлов.

---

## Модель

```
platforms
└── catalog_node (parent_id → catalog_node)
    ├── kind = 'catalog'   — папка
    ├── kind = 'doc_api'   → doc_api (prefix)
    ├── kind = 'doc_ws'    → doc_ws (url)
    ├── kind = 'doc_erd'   → doc_erd + entities / entity_relation
    ├── kind = 'markdown'  → <content_dir>/<id>.md
    └── kind = 'file'      → doc_file (filename, size) + <files_dir>/<id>/<filename>
```

Ключевое решение: **id узла и id документа — одно значение**. Полезная нагрузка
ссылается на узел первичным ключом, поэтому `/doc-show/:id` открывает документ
по тому же id, который лежит в дереве, а удаление узла уносит документ каскадом.

Имя и описание живут **только** в узле. У документа их нет: переименование —
одна операция для всех видов, и никакая таблица не может разойтись с деревом.

`parent_id IS NULL` — корень платформы. Отдельной строки-корня нет, иначе каждый
обход дерева начинался бы с особого случая.

### Инварианты

Держит их `repository/sqlite/catalog.rs`:

| Правило | Как обеспечено |
| ---------| ----------------|
| Имена уникальны среди соседей | Уникальный индекс `(platform_id, COALESCE(parent_id,''), name)` |
| Родителем может быть только каталог | Проверка `ensure_parent` при создании и переносе |
| Узел не переносится на другую платформу | Там же: сверяются `platform_id` |
| Каталог не переносится внутрь себя | Проверка по `subtree` — каскад `parent_id` цикл не ловит |
| Удаление уносит поддерево | `ON DELETE CASCADE` по `parent_id`; тела документов удаляются до строк |

### Тела документов

Markdown-текст (обзорная часть doc-api и markdown-документ) лежит файлом
`<content_dir>/<node_id>.md` — `~/.local/share/com.roman.docpoint/content` на
Linux. Имя и место документа задаёт БД, поэтому переименование и перенос диска
не касаются вовсе, а имя файла не может столкнуться с пользовательским.

### Загруженные файлы

Файл любого типа кладётся в дерево копией: `<files_dir>/<node_id>/<filename>`,
каталог на узел. Отдельно от тел документов и **под своим именем** — по
расширению система выбирает программу, а имя целиком показывает открытая
программа. Переименование узла в дереве файл на диске не трогает.

Своей страницы у такого документа нет: показывать pdf, таблицу или чертёж
приложение не умеет, поэтому `nodeRoute` отдаёт для него `null`, а открывает его
`open_file_node` через `tauri-plugin-opener` — той программой, которой этот тип
файлов открывается в системе.

## Команды бэкенда

Дерево — `service/catalog/`:

| Команда | Что делает |
| ---------| ------------|
| `read_catalog_tree(platformId)` | Все узлы платформы одним списком; дерево собирает фронтенд |
| `read_node(id)` | Один узел — страница документа знает только свой id |
| `create_node(node)` | Создаёт узел любого вида: вид выводится из `payload` |
| `rename_node(node)` | Имя и описание — один путь для всех видов |
| `move_node(node)` | Смена родителя; `parentId: null` — корень платформы |
| `delete_node(id)` | Узел с поддеревом и телами документов внутри |
| `read_markdown(id)` / `update_markdown(id, content)` | Тело markdown-документа |
| `pick_file()` | Системный диалог выбора файла: путь, имя и размер до создания узла |
| `open_file_node(id)` | Открывает загруженный файл установленной в системе программой |

Собственные поля документов правят их прежние команды: `update_doc`,
`update_websocket`. Каждая пишет и в узел (имя, описание), и в свою таблицу.

Создание документа — тот же `create_node`; `import_doc` дополнительно заливает
группы с эндпоинтами из файла.

## Фронтенд

| Слайс | Роль |
| -------| ------|
| `entities/catalog` | Тип узла, команды, сборка дерева (`buildTree`, `nodePath`, `childrenOf`), маршруты (`nodeRoute`, `catalogRoute`) |
| `entities/markdown` | Markdown-документ с телом |
| `entities/file` | Выбор файла в системном диалоге и его открытие программой |
| `features/catalog` | Диалоги создания, переименования, переноса и удаления узла |
| `features/markdown` | Автосохранение тела markdown |
| `widgets/catalog-explorer` | Проводник: путь сверху, содержимое каталога карточками по видам, перетаскивание, контекстные меню |
| `pages/platform-show` | Страница платформы = проводник; открытый каталог в `?catalog=<id>` |

Место документа в дереве страницы документов берут из самого узла
(`CatalogBackLink`), а не из состояния перехода: страница открывается и по
прямой ссылке, и в отдельном окне.

## Миграция

`0039_doc_file.sql` добавляет вид `file`: список видов задан CHECK-ограничением,
которое в SQLite меняется только пересборкой таблицы, поэтому `catalog_node`
пересоздаётся с переносом строк один в один.

`0032_catalog.sql` заводит дерево и пересобирает таблицы документов на новые
ссылки. Данные старой модели **не переносятся**: имя документа переезжало из его
таблицы в узел, а тела markdown лежали файлами вне БД — строки старого образца в
новую модель не ложатся. Платформы и окружения остаются.
