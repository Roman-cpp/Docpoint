# Формат файла импорта doc-api (документации REST API)

Файл `doc-api-example-import.json` — пример JSON-файла для импорта doc-api, документации REST API, в Docpoint. Этот документ описывает структуру таких файлов, чтобы вы могли создавать свои.

## Общая структура

Корневой объект содержит две секции:

```json
{
  "doc":    { ... },   // мета-информация о документации
  "groups": [ ... ]    // группы эндпоинтов (Auth, Users, Tasks и т. п.)
}
```

Обе секции обязательны. Если эндпоинтов нет, передайте `"groups": []`.

Модели данных (ERD) и окружения импортом не переносятся — они создаются отдельно, внутри платформы и ERD-документов. Лишние секции в файле просто игнорируются.

---

## 1. `doc` — мета-информация

Описывает документацию в целом.

```json
"doc": {
  "name": "Task Manager API",
  "desc": "REST API для управления задачами, проектами и пользователями.",
  "prefix": "/tasks"
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `name` | string | да | Название API |
| `desc` | string | да | Краткое описание назначения API |
| `prefix` | string | нет | Префикс документа, добавляется ко всем его эндпоинтам после префикса окружения (например, `/tasks`). Пустая строка или отсутствие поля — если префикса нет |

---

## 2. `groups` — группы эндпоинтов

Логическая группировка эндпоинтов (например, по ресурсу: `Auth`, `Users`, `Tasks`).

```json
"groups": [
  {
    "label": "Auth",
    "endpoints": [ ... ]
  }
]
```

### Группа

| Поле | Тип | Описание |
|------|-----|----------|
| `label` | string | Название группы, отображается в сайдбаре |
| `endpoints` | Endpoint[] | Массив эндпоинтов группы |

### Эндпоинт

```json
{
  "method": "POST",
  "path": "/auth/login",
  "name": "Login",
  "description": "Аутентификация пользователя...",
  "tags": ["public"],
  "auth": false,
  "pathParams": [],
  "queryParams": [],
  "bodyParams": [ ... ],
  "responses": { ... },
  "requests": [ ... ]
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `method` | string | HTTP-метод: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |
| `path` | string | Путь эндпоинта (можно с параметрами: `/users/{id}`) |
| `name` | string | Человекочитаемое имя эндпоинта |
| `description` | string | Подробное описание |
| `tags` | string[] | Метки (`public`, `admin`, `paginated`, `destructive` и т. п.) |
| `auth` | boolean | `true`, если требуется аутентификация |
| `pathParams` | Param[] | Описания сегментов пути. Какие сегменты есть, задаёт `path` — здесь у них появляются тип и описание |
| `queryParams` | Param[] | Параметры строки запроса |
| `bodyParams` | Param[] | Параметры тела запроса |
| `responses` | Object | Возможные ответы, ключ — HTTP-код |
| `requests` | Request[] | Готовые наборы для панели «Try it». Необязательное поле: без него эндпоинт импортируется как раньше |

### Параметр (`pathParams` / `queryParams` / `bodyParams`)

```json
{
  "name": "email",
  "type": "string",
  "required": true,
  "desc": "Email пользователя",
  "default": ""
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Имя параметра |
| `type` | string | Тип: `string`, `integer`, `boolean`, `uuid`, `datetime`, `object`, `array` |
| `required` | boolean | Обязателен ли параметр |
| `desc` | string | Описание назначения |
| `default` | string | Значение по умолчанию (пустая строка, если нет) |

У `pathParams` имя обязано совпадать с сегментом пути — импорт эндпоинта с описанием несуществующего сегмента прерывается. Описывать сегменты необязательно: неописанный доедет как обязательное поле типа `string` без пояснения.

### Ответ (`responses`)

Ключ объекта — HTTP-код (`"200"`, `"401"`, `"404"`, `"422"`, ...).

```json
"200": {
  "label": "200 OK",
  "schema": [
    { "key": "token", "type": "string", "desc": "JWT Bearer-токен", "example": "\"eyJhbGci...\"" },
    { "key": "expires_in", "type": "integer", "desc": "Срок жизни токена в секундах", "example": "3600" }
  ],
  "example": "{\n  \"token\": \"eyJhbGci...\",\n  \"expires_in\": 3600\n}"
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `label` | string | Подпись ответа (обычно `"<код> <статус>"`) |
| `schema` | SchemaField[] | Описание полей ответа |
| `example` | string | Пример тела ответа в виде форматированной JSON-строки (используйте `\n` для переносов) |

#### Поле схемы (`schema[]`)

```json
{ "key": "data[].id", "type": "uuid", "desc": "UUID записи", "example": "\"3fa85f64-...\"" }
```

| Поле | Тип | Описание |
|------|-----|----------|
| `key` | string | Путь к полю. Поддерживает вложенность (`meta.total`) и массивы (`data[].id`) |
| `type` | string | Тип значения |
| `desc` | string | Описание поля |
| `example` | string | Пример значения (опционально). Строки оборачивайте кавычками внутри: `"\"text\""` |

Для пустых ответов (`204 No Content`) используйте `schema: []` и `example: ""`.

### Тестовые запросы (`requests`)

Именованные наборы значений, которые после импорта появятся в панели «Try it» этого эндпоинта — по одной вкладке на набор. Удобно, чтобы вместе с документацией сразу приезжали готовые примеры вызовов: боевой сценарий, проверка ошибки, запрос с нестандартным заголовком.

Набор описывается по частям запроса — каждая часть лежит в своём поле и называется так же, как называется в HTTP:

```json
"requests": [
  {
    "name": "Комментарий к посту",
    "path":    { "postId": 42, "commentId": "c-7" },
    "query":   { "expand": "author" },
    "headers": { "X-Request-Id": "smoke-comment" },
    "body":    { "text": "Спасибо!" }
  }
]
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Название набора — подпись вкладки в «Try it» (`"Prod smoke"`, `"Неверный пароль"`) |
| `path` | object | Значения сегментов пути: `/posts/{postId}` → `{ "postId": 42 }` |
| `query` | object | Значения параметров строки запроса |
| `headers` | object \| Header[] | Заголовки набора |
| `body` | object \| array \| string | Тело запроса |
| `bodyMode` | string | Каким редактором открыть тело: `"fields"` — форма по полям схемы, `"raw"` — редактор JSON. По умолчанию `"fields"`. На то, что отправится, не влияет |

Порядок наборов в массиве определяет порядок вкладок. Все поля необязательны — `"requests": []` или отсутствие секции означают «наборов нет»; пустые части (`"query": {}`) можно просто не писать.

#### Сегменты пути (`path`)

Имя ключа — то, что стоит в фигурных скобках пути, сколько бы сегментов в нём ни было:

```json
"path": { "postId": 42, "commentId": "c-7" }
```

для эндпоинта с `"path": "/posts/{postId}/comments/{commentId}"`.

Значение пишется строкой, числом или булевым — в URL всё равно уезжает текст, поэтому `42` и `"42"` дают один результат. Незаполненный сегмент остаётся в адресе как `{postId}`: панель «Try it» показывает такой URL как есть, чтобы было видно, чего не хватает.

Имя, которого нет в пути, прервёт импорт с указанием эндпоинта — подставить такое значение некуда, и молчаливая потеря опечатки хуже упавшего импорта.

Чем сегмент является по смыслу, описывает `pathParams` эндпоинта — тип, пояснение и обязательность попадают и в документацию, и в подсказки полей «Try it». Сами значения живут только здесь, в наборах.

#### Параметры строки запроса (`query`)

```json
"query": { "page": 1, "limit": 20, "search": "ivan" }
```

Имя должно быть среди `queryParams` эндпоинта — панель «Try it» рисует поля по схеме и отправляет только описанные параметры, поэтому значение с чужим именем тоже прерывает импорт. Значения — строки, числа или булевы; объекты и массивы отклоняются: в строку запроса им не поместиться.

Пустая строка означает «не задано»: `"search": ""` не сохранится, и набор после импорта будет выглядеть ровно так же, как если бы поле не заполняли.

#### Заголовки (`headers`)

Обычный случай — объект «имя → значение», все заголовки включены:

```json
"headers": { "X-Request-Id": "smoke-login", "Idempotency-Key": "abc-001" }
```

Развёрнутая форма нужна, когда заголовок должен приехать выключенным (сохранится, но отправляться не будет, пока его не включат в UI) или когда важен порядок: заголовки из объекта встают по алфавиту, из массива — как написаны.

```json
"headers": [
  { "name": "X-Confirm", "value": "yes", "enabled": false }
]
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Имя заголовка (`Idempotency-Key`, `X-Request-Id`) |
| `value` | string | Значение |
| `enabled` | boolean | Необязательное, по умолчанию `true` |

`Accept` и `Content-Type` подставляются сами; заголовок с таким же именем в наборе их перекрывает — так задают, например, `application/x-www-form-urlencoded`. Токен авторизации добавляет бэкенд, если в наборе нет своего `Authorization`.

#### Тело (`body`)

Тело — цельный документ, а не набор пар «имя-значение», поэтому вложенные объекты и массивы пишутся естественно:

```json
"body": {
  "title": "Подготовить релиз",
  "meta": {
    "labels": ["release", "urgent"],
    "estimate": { "value": 8, "unit": "hours" }
  }
}
```

Типы берутся из самого JSON: `8` уйдёт числом, `true` — булевым, `"8"` — строкой. Схема эндпоинта на это не влияет — она описывает документацию, а не подменяет то, что вы написали в теле.

Строкой тело пишут, когда оно не JSON — например, form-urlencoded:

```json
"body": "title=Подготовить релиз&priority=high"
```

Такое тело уходит дословно, только с подстановкой переменных. Учтите: панель «Try it» не даёт отправить тело, которое выглядит как сломанный JSON, — импортировать такой набор можно, но кнопка Send на нём будет заблокирована.

Ссылки на переменные окружения работают внутри тела: `"password": "{{DEFAULT_PASSWORD}}"`. Подстановка происходит при отправке. Если поле описано в `bodyParams` числовым или булевым, подставленное значение приводится к этому типу — иначе `{{PORT}}` уехал бы строкой.

Отсутствие `body` или `""` означают, что тела нет. У `GET` и `HEAD` тело не отправляется никогда.

#### Прежняя форма: `values[]`

До появления `path` и `query` те же значения писались одним списком с пометкой вида:

```json
"values": [
  { "kind": "path",  "name": "postId", "value": "42" },
  { "kind": "query", "name": "page",   "value": "1" }
]
```

Такие файлы по-прежнему импортируются, но в новых лучше использовать `path` и `query`: имя параметра сразу видно рядом с его значением, дубликаты невозможны, а `kind: "body"` — частая ошибка старой формы — просто не может возникнуть (тело живёт в `body`). Если один и тот же параметр задан обоими способами, побеждает значение из `path`/`query`.

#### Что не переносится

`id`, `endpointId` и `sortOrd` в файле игнорируются, даже если вы их укажете: при импорте эндпоинты и наборы получают свежие идентификаторы. Благодаря этому один и тот же файл можно импортировать несколько раз — записи не конфликтуют между собой.

## Чек-лист перед импортом

- [ ] JSON валиден (используйте линтер или `jq .`)
- [ ] У каждого эндпоинта есть `method`, `path`, `name`, `description`
- [ ] Все коды ответов — строки (`"200"`, не `200`)
- [ ] Поля `example` — это **строки**, а не объекты. JSON внутри экранируется (`\"`, `\n`)
- [ ] Пустые массивы передаются как `[]`, а не отсутствуют
- [ ] Имена в `pathParams` и ключи `requests[].path` совпадают с сегментами в фигурных скобках пути
- [ ] Ключи `requests[].query` описаны в `queryParams` эндпоинта
- [ ] В `path` и `query` значения — строки, числа или булевы, но не объекты и не массивы
- [ ] Тело запроса лежит в `requests[].body`, а не среди значений параметров

## Минимальный шаблон

```json
{
  "doc": {
    "name": "My API",
    "desc": "Краткое описание"
  },
  "groups": [
    {
      "label": "Default",
      "endpoints": [
        {
          "method": "GET",
          "path": "/ping",
          "name": "Ping",
          "description": "Проверка доступности.",
          "tags": [],
          "auth": false,
          "queryParams": [],
          "bodyParams": [],
          "responses": {
            "200": {
              "label": "200 OK",
              "schema": [
                { "key": "status", "type": "string", "desc": "Статус", "example": "\"ok\"" }
              ],
              "example": "{\n  \"status\": \"ok\"\n}"
            }
          }
        }
      ]
    }
  ]
}
```

Полный пример доступен в [doc-api-example-import.json](doc-api-example-import.json).
