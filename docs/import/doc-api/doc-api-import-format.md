# Формат файла импорта doc-api (документации REST API)

Файл `doc-api-example-import.json` — пример JSON-файла для импорта doc-api, документации REST API, в Docpoint. Этот документ описывает структуру таких файлов, чтобы вы могли создавать свои.

## Общая структура

Корневой объект содержит две секции:

```json
{
  "doc":    { ... },   // id документа, имя и префикс
  "groups": [ ... ]    // группы эндпоинтов (Auth, Users, Tasks и т. п.)
}
```

Обе секции обязательны. Если эндпоинтов нет, передайте `"groups": []`.

Модели данных (ERD) и окружения импортом не переносятся — они создаются отдельно, внутри платформы и ERD-документов. Лишние секции в файле просто игнорируются.

---

## 1. `doc` — мета-информация

Описывает документацию в целом.

```json
"doc": {
  "id": "3f6c1b2a-9a1e-4f7c-8f21-6f1a2b9d5c40",
  "name": "Task Manager API",
  "prefix": "/api/v1"
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `id` | string | нет | Ключ документа. Импорт ищет документ с этим id и дописывает файл в него; если такого документа нет — заводит его под этим же id. Без `id` каждый импорт создаёт новый документ |
| `name` | string | да | Название API. Становится именем документа при его создании |
| `prefix` | string | нет | Префикс документа, добавляется ко всем его эндпоинтам после префикса окружения (например, `/api/v1`). Пустая строка или отсутствие поля — если префикса нет |

Больше в заголовке ничего не читается. Описания у документа нет — его роль
играет само содержимое, — а версия API живёт в `prefix`, поэтому поля `desc`
и `version` из файлов прежних версий формата просто игнорируются.

### `id` — какой он должен быть

Годится любая строка, лишь бы она была уникальной в пределах установки:
`3f6c1b2a-…` из экспорта, `task-manager-api`, `billing/v2`. Смысла внутри id
нет — приложение только сравнивает его с id документов, которые уже есть.

Проще всего не придумывать его самому: **Экспортировать** у документа отдаёт
файл, в котором `id` уже стоит. Правьте этот файл и импортируйте обратно —
изменения приедут в тот же документ.

Выгруженный файл содержит всё, что приложение знает об эндпоинтах: описание,
параметры всех четырёх видов, структуру тела и ответов с примечаниями и
наборы «Try it» со значениями. Поэтому экспорт и импорт того же файла ничего
не теряют, и такой файл годится и как резервная копия, и как то, что кладут в
репозиторий рядом с кодом.

Если id занят не документом API, а каталогом или markdown-файлом, импорт
остановится: id уже не свободен, и заводить рядом второй документ бессмысленно.

## 2. `groups` — группы эндпоинтов

Логическая группировка эндпоинтов (например, по ресурсу: `Auth`, `Users`, `Tasks`).

```json
"groups": [
  {
    "label": "Auth",
    "endpoints": [ ... ]
  }
]
```

### Группа

| Поле | Тип | Описание |
|------|-----|----------|
| `label` | string | Название группы, отображается в сайдбаре |
| `endpoints` | Endpoint[] | Массив эндпоинтов группы |

### Эндпоинт

```json
{
  "method": "POST",
  "path": "/auth/login",
  "name": "Login",
  "description": "Аутентификация пользователя...",
  "auth": false,
  "pathParams": [],
  "queryParams": [],
  "headerParams": [],
  "cookieParams": [],
  "body": { ... },
  "bodyFields": [ ... ],
  "responses": { ... },
  "requests": [ ... ]
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `method` | string | HTTP-метод: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |
| `path` | string | Путь эндпоинта (можно с параметрами: `/users/{id}`) |
| `name` | string | Человекочитаемое имя эндпоинта |
| `description` | string | Подробное описание |
| `auth` | boolean | `true`, если требуется аутентификация |
| `pathParams` | Param[] | Описания сегментов пути. Какие сегменты есть, задаёт `path` — здесь у них появляются тип и описание |
| `queryParams` | Param[] | Параметры строки запроса |
| `headerParams` | Param[] | Заголовки, которые ожидает эндпоинт: `Idempotency-Key`, `X-Request-Id` |
| `cookieParams` | Param[] | Куки, которые ожидает эндпоинт |
| `body` | object \| array \| string | Структура тела запроса — настоящий JSON, а не строка. Форму и типы задаёт он сам |
| `bodyFields` | Field[] | Примечания к полям тела: описание, обязательность, уточнение типа |
| `responses` | Object | Возможные ответы, ключ — HTTP-код |
| `requests` | Request[] | Готовые наборы для панели «Try it». Необязательное поле: без него эндпоинт импортируется как раньше |

### Параметр (`pathParams` / `queryParams` / `headerParams` / `cookieParams`)

```json
{
  "name": "email",
  "type": "string",
  "required": true,
  "desc": "Email пользователя",
  "default": ""
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Имя параметра |
| `type` | string | Тип: `string`, `integer`, `boolean`, `uuid`, `datetime`, `object`, `array` |
| `required` | boolean | Обязателен ли параметр |
| `desc` | string | Описание назначения |
| `default` | string | Значение по умолчанию (пустая строка, если нет) |
| `value` | string | Имя переменной окружения, закреплённой за параметром в «Try it»: `"API_TOKEN"` — и панель сама подставит `{{API_TOKEN}}`, пока в набор не вписано своё. Без привязки поле не пишется |

Все четыре вида устроены одинаково — различается только место, куда параметр едет в запросе. Это то же деление, что `in` у OpenAPI.

У `pathParams` имя обязано совпадать с сегментом пути — импорт эндпоинта с описанием несуществующего сегмента прерывается. Описывать сегменты необязательно: неописанный доедет как обязательное поле типа `string` без пояснения.

### Тело запроса (`body` и `bodyFields`)

Тело описывается так, как выглядит на самом деле — целым JSON-документом:

```json
"body": {
  "title": "Подготовить релиз",
  "priority": "high",
  "meta": {
    "labels": ["release"],
    "estimate": { "value": 8, "unit": "hours" }
  }
},
"bodyFields": [
  { "path": "title", "desc": "Заголовок задачи", "required": true },
  { "path": "meta.labels[]", "desc": "Метки" },
  { "path": "meta.estimate.value", "desc": "Оценка", "format": "integer" }
]
```

Документ задаёт форму и типы: `8` — число, `true` — булево, `[]` — массив. Вкладывать можно сколько угодно, отдельного описания для этого не нужно.

`bodyFields` добавляет то, чего в самом JSON не видно.

| Поле | Тип | Описание |
|------|-----|----------|
| `path` | string | Путь к полю внутри документа: `title`, `meta.total`, `data[].id`. Скобки означают «элемент массива»: у всех элементов форма одна, и описание у них одно |
| `desc` | string | Описание назначения |
| `required` | boolean | Обязательно ли поле. По умолчанию `false` |
| `format` | string | Уточнение типа, которого JSON не различает: `uuid`, `datetime`, `date`, `email`, `integer`. Пусто — тип берётся из документа |

Примечание на путь, которого в документе нет, не ошибка: так описывают необязательное поле, которого в примере намеренно не оказалось. Импорт его сохранит, а страница покажет отдельной строкой «описано, но в структуре нет». А вот два примечания на один путь импорт остановят — непонятно, какое настоящее.

Тело, которое JSON не является (форма, XML, текст), пишется строкой:

```json
"body": "title=Подготовить релиз&priority=high"
```

Полей у такого тела не будет — их неоткуда взять.

#### Прежняя форма: `bodyParams`

До перехода на документ тело описывалось плоским списком полей:

```json
"bodyParams": [
  { "name": "title", "type": "string", "required": true, "desc": "Заголовок" }
]
```

Такие файлы по-прежнему импортируются: список сворачивается в документ — по полю на ключ, значение подставляется по типу (`string` → `"<title>"`, `integer` → `0`), а описания уезжают в `bodyFields`. Но выразить вложенность он по-прежнему не может, поэтому в новых файлах лучше писать `body`. Если в файле есть и то и другое, побеждает `body`.

### Ответ (`responses`)

Ключ объекта — HTTP-код (`"200"`, `"401"`, `"404"`, `"422"`, ...). Ответ
описывается так же, как тело запроса: структура документом и примечания к её
полям. Документ здесь же и пример — другого «как это выглядит» у ответа не
бывает.

```json
"200": {
  "label": "200 OK",
  "body": {
    "data": [{ "id": "1b9d6bcd-…", "title": "Implement login page" }],
    "meta": { "total": 37 }
  },
  "fields": [
    { "path": "data[].id", "desc": "UUID задачи", "format": "uuid" },
    { "path": "data[].title", "desc": "Заголовок задачи" },
    { "path": "meta.total", "desc": "Всего задач", "format": "integer" }
  ]
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `label` | string | Подпись ответа (обычно `"<код> <статус>"`) |
| `body` | object \| array \| string | Структура ответа. Массив в корне описывается по своему элементу, и путь к его полям начинается со скобок: `[].symbol` |
| `fields` | Field[] | Примечания к полям: те же `path`, `desc`, `required`, `format`, что у тела запроса |

Для пустого ответа (`204 No Content`) достаточно одной подписи: `body` и
`fields` можно не писать.

Ответ, который не является JSON — метрики Prometheus, обычный текст, — пишется
строкой. Полей у него не будет, зато сам ответ виден:

```json
"200": { "label": "200 OK", "body": "# HELP requests_total\n# TYPE counter" }
```

#### Прежняя форма: `schema` и `example`

До перехода на документ ответ описывался списком ключей рядом с примером:

```json
"200": {
  "label": "200 OK",
  "schema": [{ "key": "token", "type": "string", "desc": "JWT", "example": "\"eyJ\"" }],
  "example": "{\n  \"token\": \"eyJ...\"\n}"
}
```

Такие файлы читаются по-прежнему: пример становится структурой, ключи —
примечаниями, а значение поля дописывается в структуру, если такого пути в ней
ещё нет и ветка под него есть. Структуру под путь без ветки импорт не
выдумывает — поле останется примечанием без места, и страница покажет его
отдельной строкой.

### Тестовые запросы (`requests`)

Именованные наборы значений, которые после импорта появятся в панели «Try it» этого эндпоинта — по одной вкладке на набор. Удобно, чтобы вместе с документацией сразу приезжали готовые примеры вызовов: боевой сценарий, проверка ошибки, запрос с нестандартным заголовком.

Набор описывается по частям запроса — каждая часть лежит в своём поле и называется так же, как называется в HTTP:

```json
"requests": [
  {
    "name": "Комментарий к посту",
    "path":    { "postId": 42, "commentId": "c-7" },
    "query":   { "expand": "author" },
    "headers": { "X-Request-Id": "smoke-comment" },
    "body":    { "text": "Спасибо!" }
  }
]
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Название набора — подпись вкладки в «Try it» (`"Prod smoke"`, `"Неверный пароль"`) |
| `path` | object | Значения сегментов пути: `/posts/{postId}` → `{ "postId": 42 }` |
| `query` | object | Значения параметров строки запроса |
| `headers` | object \| Header[] | Заголовки набора |
| `cookies` | object \| Cookie[] | Куки набора: собираются в заголовок `Cookie` при отправке |
| `body` | object \| array \| string | Тело запроса |
| `bodyMode` | string | Каким редактором открыть тело: `"fields"` — форма по полям схемы, `"raw"` — редактор JSON. По умолчанию `"fields"`. На то, что отправится, не влияет |

Порядок наборов в массиве определяет порядок вкладок. Все поля необязательны — `"requests": []` или отсутствие секции означают «наборов нет»; пустые части (`"query": {}`) можно просто не писать.

Экспорт документа пишет наборы вместе с описанием, так что выгруженный файл содержит и то, что настроено в панели: значения сегментов, строки запроса, заголовки, куки и тело каждого набора.

#### Сегменты пути (`path`)

Имя ключа — то, что стоит в фигурных скобках пути, сколько бы сегментов в нём ни было:

```json
"path": { "postId": 42, "commentId": "c-7" }
```

для эндпоинта с `"path": "/posts/{postId}/comments/{commentId}"`.

Значение пишется строкой, числом или булевым — в URL всё равно уезжает текст, поэтому `42` и `"42"` дают один результат. Незаполненный сегмент остаётся в адресе как `{postId}`: панель «Try it» показывает такой URL как есть, чтобы было видно, чего не хватает.

Имя, которого нет в пути, прервёт импорт с указанием эндпоинта — подставить такое значение некуда, и молчаливая потеря опечатки хуже упавшего импорта.

Чем сегмент является по смыслу, описывает `pathParams` эндпоинта — тип, пояснение и обязательность попадают и в документацию, и в подсказки полей «Try it». Сами значения живут только здесь, в наборах.

#### Параметры строки запроса (`query`)

```json
"query": { "page": 1, "limit": 20, "search": "ivan" }
```

Имя должно быть среди `queryParams` эндпоинта — панель «Try it» рисует поля по схеме и отправляет только описанные параметры, поэтому значение с чужим именем тоже прерывает импорт. Значения — строки, числа или булевы; объекты и массивы отклоняются: в строку запроса им не поместиться.

Пустая строка означает «не задано»: `"search": ""` не сохранится, и набор после импорта будет выглядеть ровно так же, как если бы поле не заполняли.

#### Заголовки (`headers`)

Обычный случай — объект «имя → значение», все заголовки включены:

```json
"headers": { "X-Request-Id": "smoke-login", "Idempotency-Key": "abc-001" }
```

Развёрнутая форма нужна, когда заголовок должен приехать выключенным (сохранится, но отправляться не будет, пока его не включат в UI) или когда важен порядок: заголовки из объекта встают по алфавиту, из массива — как написаны.

```json
"headers": [
  { "name": "X-Confirm", "value": "yes", "enabled": false }
]
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Имя заголовка (`Idempotency-Key`, `X-Request-Id`) |
| `value` | string | Значение |
| `enabled` | boolean | Необязательное, по умолчанию `true` |

`Accept` и `Content-Type` подставляются сами; заголовок с таким же именем в наборе их перекрывает — так задают, например, `application/x-www-form-urlencoded`. Токен авторизации добавляет бэкенд, если в наборе нет своего `Authorization`.

#### Куки (`cookies`)

Пишутся так же, как заголовки: объектом, когда все включены, и списком, когда какая-то должна приехать выключенной.

```json
"cookies": { "session": "abc123", "theme": "dark" }
```

При отправке они собираются в один заголовок `Cookie`. Туда же бэкенд домешивает куки сессии выбранного окружения — но одноимённую вашу не перетирает: то, что вписано в наборе, важнее сохранённой сессии.

#### Тело (`body`)

Тело — цельный документ, а не набор пар «имя-значение», поэтому вложенные объекты и массивы пишутся естественно:

```json
"body": {
  "title": "Подготовить релиз",
  "meta": {
    "labels": ["release", "urgent"],
    "estimate": { "value": 8, "unit": "hours" }
  }
}
```

Типы берутся из самого JSON: `8` уйдёт числом, `true` — булевым, `"8"` — строкой. Схема эндпоинта на это не влияет — она описывает документацию, а не подменяет то, что вы написали в теле.

Строкой тело пишут, когда оно не JSON — например, form-urlencoded:

```json
"body": "title=Подготовить релиз&priority=high"
```

Такое тело уходит дословно, только с подстановкой переменных. Учтите: панель «Try it» не даёт отправить тело, которое выглядит как сломанный JSON, — импортировать такой набор можно, но кнопка Send на нём будет заблокирована.

Ссылки на переменные окружения работают внутри тела: `"password": "{{DEFAULT_PASSWORD}}"`. Подстановка происходит при отправке. Если поле описано в структуре числовым или булевым, подставленное значение приводится к этому типу — иначе `{{PORT}}` уехал бы строкой. Работает на любой глубине: тип берётся по пути поля.

Отсутствие `body` или `""` означают, что тела нет. У `GET` и `HEAD` тело не отправляется никогда.

#### Прежняя форма: `values[]`

До появления `path` и `query` те же значения писались одним списком с пометкой вида:

```json
"values": [
  { "kind": "path",  "name": "postId", "value": "42" },
  { "kind": "query", "name": "page",   "value": "1" }
]
```

Такие файлы по-прежнему импортируются, но в новых лучше использовать `path` и `query`: имя параметра сразу видно рядом с его значением, дубликаты невозможны, а `kind: "body"` — частая ошибка старой формы — просто не может возникнуть (тело живёт в `body`). Если один и тот же параметр задан обоими способами, побеждает значение из `path`/`query`.

#### Что не переносится

`id`, `endpointId` и `sortOrd` в файле игнорируются, даже если вы их укажете: при импорте эндпоинты и наборы получают свежие идентификаторы. Благодаря этому один и тот же файл можно импортировать несколько раз — записи не конфликтуют между собой. По той же причине повторный импорт файла в существующий документ опознаёт записи по смыслу, а не по идентификаторам — см. [Обновление документа из файла](#обновление-документа-из-файла).

## Обновление документа из файла

Импорт один и тот же: **Импорт → API-документ (JSON)**. Что произойдёт,
решает `id` в файле.

- **Документа с таким id нет** — он создаётся в открытом каталоге, под этим же
  id. Ровно так импорт работал всегда.
- **Документ с таким id есть** — файл дописывается в него. Дописали в файл
  новый эндпоинт, импортировали снова — добавится только он. Документ не
  пересоздаётся: его ссылки, окружения и место в дереве остаются.

Выбирать документ вручную не нужно и нельзя — его называет сам файл. В тосте
после импорта видно, куда прилетело: «Документ обновлён — «Task Manager API»,
добавлено эндпоинтов: 1, обновлено: 11».

### Как содержимое файла сопоставляется с документом

Внутри документа записи опознаются не по id (у групп и эндпоинтов их в файле
нет), а по смыслу:

| Что | По чему опознаётся |
|-----|--------------------|
| Группа | `label` |
| Эндпоинт | пара `method` + `path`, по всему документу целиком |
| Набор «Try it» | `name` внутри своего эндпоинта |

Эндпоинт ищется по всему документу, а не внутри группы: перенесли его в файле
в другую группу — он переедет туда же и в документе, а не задвоится.

Обратная сторона: **правка `method` или `path` — это новый эндпоинт**. Прежний
по такому ключу не находится и останется в документе рядом с новым; удалить его
нужно самому. Переименование группы проходит мягче — эндпоинты найдутся по
своим сигнатурам и переедут в новую группу, но прежняя останется пустой.

### Что делает импорт с найденным документом

- **Находит запись** — перезаписывает описание: имя, описание, признак
  авторизации, параметры, ответы. Наборы из файла ложатся поверх одноимённых.
- **Не находит** — добавляет: новая группа встаёт в конец списка, новый
  эндпоинт — в конец своей группы.
- **Чего в файле нет — не трогает.** Импорт ничего не удаляет: убрать эндпоинт
  из файла — не то же самое, что удалить его из документа.

Последнее важно, потому что рядом с описанием живут данные, которых в файле не
бывает: значения параметров, привязки к переменным окружения (`{{TOKEN}}`) и
наборы «Try it», заведённые руками в панели. Всё это импорт переживает.

Имя документа и его место в дереве файл тоже не меняет — переименовали документ
у себя, он всё равно найдётся по id и останется с вашим именем. Из заголовка
применяется только `prefix`, да и то если он в файле есть.

### Когда импорт остановится

Файл проверяется целиком **до** первой записи в базу, так что документ либо
обновляется, либо остаётся нетронутым. Импорт откажется работать, если:

- в файле два эндпоинта с одинаковыми `method` и `path` либо две группы с
  одинаковым `label` — непонятно, какое из описаний настоящее;
- то же самое уже есть в самом документе (две группы с одним названием,
  заведённые руками) — непонятно, какую из них обновлять;
- у эндпоинта неизвестный `method`, описан несуществующий сегмент пути или
  набор ссылается на параметр, которого нет в схеме;
- `id` из файла занят узлом другого вида;
- документ создаётся, а в открытом каталоге уже есть свой с таким же именем, —
  имена соседей уникальны, как в проводнике.

## Чек-лист перед импортом

- [ ] JSON валиден (используйте линтер или `jq .`)
- [ ] Если файл должен обновлять уже заведённый документ — в `doc.id` стоит его id
- [ ] У каждого эндпоинта есть `method`, `path`, `name`, `description`
- [ ] Все коды ответов — строки (`"200"`, не `200`)
- [ ] Структура (`body` у эндпоинта и у ответа) написана объектом, а не строкой с экранированием
- [ ] Пустые секции можно не писать вовсе: отсутствующий `queryParams` и `"queryParams": []` означают одно и то же
- [ ] Имена в `pathParams` и ключи `requests[].path` совпадают с сегментами в фигурных скобках пути
- [ ] Ключи `requests[].query` описаны в `queryParams` эндпоинта
- [ ] В `path` и `query` значения — строки, числа или булевы, но не объекты и не массивы
- [ ] Тело запроса лежит в `requests[].body`, а не среди значений параметров
- [ ] Значения заголовков и кук — в `requests[].headers` и `requests[].cookies`, а их описания — в `headerParams` и `cookieParams` эндпоинта

## Минимальный шаблон

```json
{
  "doc": {
    "id": "my-api",
    "name": "My API",
    "prefix": ""
  },
  "groups": [
    {
      "label": "Default",
      "endpoints": [
        {
          "method": "GET",
          "path": "/ping",
          "name": "Ping",
          "description": "Проверка доступности.",
          "auth": false,
          "queryParams": [],
          "responses": {
            "200": {
              "label": "200 OK",
              "body": { "status": "ok" },
              "fields": [{ "path": "status", "desc": "Статус" }]
            }
          }
        }
      ]
    }
  ]
}
```

Полный пример доступен в [doc-api-example-import.json](doc-api-example-import.json).
