# Импорт ERD из базы данных

Второй способ получить ERD-диаграмму, кроме [файла импорта](doc-erd-import-format.md): подключиться к живой базе и прочитать её схему. Парный документ описывает формат файла; этот — что именно читается из СУБД и во что превращается.

## Точка входа

Пункт «Импорт → ERD из базы данных…» в проводнике платформы (`CatalogExplorer`) — в выпадающем меню шапки и в контекстном меню пустого места. Диаграмма создаётся в **открытом каталоге**, как и при импорте из файла, и сразу открывается на холсте.

## Что нужно для подключения

| СУБД | Поля |
|------|------|
| PostgreSQL | хост, порт (5432), пользователь, пароль, база, режим TLS |
| MySQL | хост, порт (3306), пользователь, пароль, база, режим TLS |
| SQLite | путь к файлу — выбирается системным диалогом |

**Подключения не сохраняются.** Ни адреса, ни пароля в базе Docpoint не остаётся: реквизиты живут в полях формы, пока мастер открыт, и уходят на бэкенд с каждым вызовом. Закрыли мастер — вводить заново.

Режимы TLS: `prefer` (по умолчанию — попробовать, но не настаивать), `disable`, `require` (шифровать, сертификат не проверять — годится для внутреннего самоподписанного) и `verify-full` (с проверкой). Если `verify-full` не проходит из-за внутреннего центра сертификации, помогает `require`.

Прав достаточно на чтение системного каталога. Данные таблиц **не читаются вовсе** — поэтому и поле «пример значения» у импортированных колонок пустое.

## Что читается

| | схемы | таблицы и колонки | ключи | комментарии и перечисления |
|---|---|---|---|---|
| **PostgreSQL** | `pg_namespace` без системных | `pg_attribute` + `format_type` | `pg_constraint` (PK и FK, включая составные) | `col_description`/`obj_description`, значения из `pg_enum` |
| **MySQL** | `information_schema.SCHEMATA` без системных | `information_schema.COLUMNS` (`COLUMN_TYPE`) | `KEY_COLUMN_USAGE` в пределах той же базы | `COLUMN_COMMENT`/`TABLE_COMMENT`, значения из `enum(...)` |
| **SQLite** | одна, `main` | `sqlite_master` + `pragma_table_info` | `pragma_foreign_key_list` | нет ни того, ни другого |

Диаграмма собирается **по одной схеме за раз**: связи адресуют таблицы именами, а имена уникальны только внутри схемы.

## Во что превращается

| Поле ERD | Откуда |
|---|---|
| `type` | родной тип как есть: `varchar(255)`, `numeric(12,2)`, `jsonb`, `timestamptz`. Длинные написания PostgreSQL сокращаются до привычных (`character varying(255)` → `varchar(255)`) |
| `pk` | входит в первичный ключ; у составного помечены все колонки |
| `nullable` | колонка допускает NULL |
| `req` | обратное к `nullable` — это отражение самого ограничения колонки, а не «обязательно при вставке»: у колонки NOT NULL с DEFAULT флаг тоже стоит, а её DEFAULT уходит в заметку |
| `desc` | комментарий колонки или таблицы — человеческий текст остаётся отдельно от машинного |
| `note` | то, чего не видно по флагам: `DEFAULT now()`, `FK → users.id`, `AUTO_INCREMENT`, значения перечисления |
| `example` | всегда пусто: пример значения означал бы чтение чужих данных |
| `enum` | значения перечисления (PostgreSQL — тип-перечисление, MySQL — `enum(...)`) |

Значения перечисления дублируются текстом в `note` намеренно: редактор полей хранит `enum` только у поля с типом `enum`, а в типе стоит родное имя (`order_status`) — без дубля первая же ручная правка таблицы стёрла бы значения.

## Что отбрасывается и почему

Живая схема почти всегда содержит то, чего холст не рисует. Такие места не отменяют импорт — они пропускаются, а причина попадает в список под таблицами на шаге выбора:

| Случай | Что делает импорт |
|---|---|
| **Самоссылающийся ключ** (`employees.manager_id → employees.id`) | связь пропускается: холст пока не рисует петли |
| **Составной внешний ключ** | остаётся связь по первой паре колонок |
| **Одна и та же пара колонок дважды** | остаётся одна связь: на четвёрку концов в базе стоит UNIQUE |
| **Ссылка на таблицу вне схемы** | связь пропускается: рисовать её не на чем |
| **Таблица снята галочкой** | вместе с ней уходят и её связи |

Пустая схема — не ошибка: мастер покажет пустой список и скажет, что таблиц нет.

## Раскладка и дальнейшая жизнь диаграммы

Координаты назначает импорт — той же сеткой, что и [импорт из файла](doc-erd-import-format.md#раскладка). Дальше диаграмма живёт своей жизнью: таблицы двигаются мышью, связи добавляются и удаляются на холсте. **Обратной связи с базой нет** — это снимок, а не синхронизация. Повторный импорт создаёт новую диаграмму рядом, а не обновляет старую.

## Ограничения

- NoSQL пока не поддержан. Место под него в коде оставлено: адаптер реализует единственный трейт `SchemaSource` (`domain/db_import/schema/repository.rs`) и отдаёт тот же снимок схемы, что и реляционные.
- Представления (`VIEW`) не импортируются — только базовые таблицы.
- Диаграмма из сотни таблиц нечитаема: выбирайте нужные на втором шаге, мастер предупредит, если таблиц много.
