# Формат файла импорта ERD

Файл `doc-erd-example-import.json` — пример JSON-файла для импорта ERD-диаграммы в Docpoint.

Диаграмма целиком описывается своими таблицами и связями: собственных полей у узла-диаграммы нет. Поэтому файл — это просто список таблиц с колонками плюс список связей между колонками.

## Точка входа

Пункт «Импорт → ERD-диаграмма (JSON)» в проводнике платформы (`CatalogExplorer`) — в выпадающем меню шапки и в контекстном меню пустого места. Создаёт узел-диаграмму из блока `erd` в **открытом каталоге** — место в дереве в файле не хранится.

## Общая структура

```json
{
  "version": 1,
  "erd": { ... },        // обязательно: имя и описание диаграммы
  "tables": [ ... ],     // обязательно: непустой список таблиц
  "relations": [ ... ]   // необязательно: связи между колонками
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `version` | number | да | Версия формата файла (сейчас всегда `1`) |
| `erd` | object | да | Имя и описание диаграммы — из них создаётся узел дерева |
| `tables` | Table[] | да | Непустой список таблиц |
| `relations` | Relation[] | нет | Связи между колонками. Диаграмма из несвязанных таблиц законна |

---

## `erd` — описание диаграммы

```json
"erd": {
  "name": "Биллинг",
  "desc": "Аккаунты, их подписки и платежи по ним."
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `name` | string | да | Название диаграммы — имя узла в дереве |
| `desc` | string | нет | Описание. По умолчанию — пустая строка |

---

## `tables` — таблицы

```json
{
  "name": "accounts",
  "desc": "Аккаунт клиента.",
  "columns": [ ... ]
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `name` | string | да | Имя таблицы. На него ссылаются связи, поэтому имена должны быть **уникальны** в пределах файла |
| `desc` | string | нет | Описание таблицы. По умолчанию — пустая строка |
| `columns` | Column[] | да | Непустой список колонок |

### Раскладка

Координат в файле нет. Положение таблиц целиком назначает импорт: он раскладывает их сеткой — колонок примерно корень из числа таблиц, внутри колонки таблицы стоят стопкой — и сразу сохраняет результат. Дальше положение живёт в базе и меняется перетаскиванием, а не файлом.

Порядок таблиц в файле — это порядок раскладки, так что связанные таблицы удобно ставить рядом.

---

## `columns` — колонки

```json
{
  "name": "archived_at",
  "type": "datetime",
  "nullable": true,
  "note": "Заполняется при закрытии аккаунта."
}
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `name` | string | да | Имя колонки. На него ссылаются связи, поэтому имена должны быть **уникальны** в пределах таблицы |
| `type` | string | нет | Тип. Свободная строка — диаграмма его только показывает и ни с чем не сверяет, годится и `uuid`, и `numeric(12,2)`. По умолчанию `"string"` |
| `pk` | boolean | нет | Первичный ключ — зелёная иконка ключа. По умолчанию `false` |
| `req` | boolean | нет | Обязательное поле. По умолчанию `false` |
| `nullable` | boolean | нет | Допускает NULL — полая ромбовидная иконка. По умолчанию `false` |
| `desc` | string | нет | Описание колонки |
| `note` | string | нет | Заметка |
| `example` | string | нет | Пример значения |
| `enum` | (string \| {val, desc})[] | нет | Допустимые значения |

Иконку колонки выбирает сам холст, и `pk` важнее всего: `pk` → ключ, иначе сторона внешнего ключа какой-нибудь связи → звено, иначе `nullable` → полый ромб, иначе сплошной. Поэтому помечать внешний ключ вручную не нужно — достаточно описать связь.

### `enum` — две формы

Короткая, когда описания не нужны:

```json
"enum": ["active", "suspended", "closed"]
```

Полная, когда нужны:

```json
"enum": [
  { "val": "free", "desc": "Бесплатный тариф, без счетов." },
  { "val": "pro", "desc": "Ежемесячная оплата." }
]
```

---

## `relations` — связи

```json
{ "from": "accounts.id", "to": "subscriptions.account_id" }
```

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `from` | string | да | Сторона первичного ключа («один»), адрес вида `таблица.колонка` |
| `to` | string | да | Сторона внешнего ключа («многие»), адрес вида `таблица.колонка` |

Направление важно: `from` — это «один», `to` — «многие». Именно так холст рисует лапку вороны и так же расставляет иконки внешних ключей.

Адрес делится по **последней** точке, поэтому имя таблицы может быть с квалификатором схемы (`public.users.id` → таблица `public.users`, колонка `id`). Точка внутри имени колонки не поддерживается.

---

## Ограничения

Всё это проверяется до первой записи в базу, и ошибка называет конкретную таблицу, колонку или связь:

- **Имена таблиц уникальны** в файле, **имена колонок** — в пределах таблицы. Иначе адрес связи неоднозначен.
- **Оба конца связи должны существовать.** Ссылка на неописанную таблицу или колонку — ошибка, а не молчаливо пропущенная связь.
- **Таблица не может ссылаться сама на себя.** Холст пока не умеет рисовать такие связи, поэтому импорт их отклоняет. Это ограничение отрисовки, а не схемы, — самоссылающийся FK (`parent_id → id`) придётся описать комментарием.
- **У пары колонок только одна связь.** Та же пара в обратную сторону — не вторая связь, а спор о том, где сторона первичного ключа.
- **Булевы поля строго булевы.** `"pk": "true"` или `"pk": 1` — ошибка, а не молчаливое приведение: почти всегда это опечатка.

## Чек-лист перед импортом

- [ ] JSON валиден (`jq .`)
- [ ] `version` равен `1`
- [ ] `erd.name` заполнен
- [ ] У каждой таблицы есть `name` и непустой `columns`
- [ ] У каждой колонки есть `name`
- [ ] Имена таблиц не повторяются, имена колонок внутри таблицы — тоже
- [ ] Каждый конец связи указывает на существующую колонку
- [ ] В проводнике открыт тот каталог, куда должна лечь диаграмма

## Минимальный шаблон

```json
{
  "version": 1,
  "erd": { "name": "Схема" },
  "tables": [
    {
      "name": "users",
      "columns": [
        { "name": "id", "type": "uuid", "pk": true },
        { "name": "email", "type": "string", "req": true }
      ]
    },
    {
      "name": "sessions",
      "columns": [
        { "name": "id", "type": "uuid", "pk": true },
        { "name": "user_id", "type": "uuid", "req": true }
      ]
    }
  ],
  "relations": [{ "from": "users.id", "to": "sessions.user_id" }]
}
```

Полный пример доступен в [doc-erd-example-import.json](doc-erd-example-import.json).

Схему можно не описывать руками, а прочитать из живой базы — см. [импорт ERD из базы данных](doc-erd-db-import.md).
